# Sales Performance Dashboard

Дашборд эффективности продаж для руководителя отдела: ключевые показатели за период с динамикой к предыдущему периоду и рейтинг менеджеров. Все расчёты выполняются на сервере, фронтенд только отображает готовые данные.

| Слой | Технологии |
|---|---|
| Backend | C# · .NET 8 · ASP.NET Core Minimal API · EF Core 8 · Npgsql |
| База данных | PostgreSQL 16 |
| Frontend | React 18 · TypeScript · Vite · TanStack Query |
| Документация API | Swagger (Swashbuckle) + Scalar |
| Тесты | xUnit (backend) · Vitest + Testing Library (frontend) |
| Инфраструктура | Docker Compose · nginx |

## Быстрый старт

Нужен только **Docker Desktop**.

```bash
docker compose up --build
```

Команда поднимает три контейнера: PostgreSQL, API и фронтенд. При старте API сам:

1. создаёт базу `sales_dashboard`, если её нет;
2. применяет миграции EF Core;
3. заполняет пустую базу тестовыми данными.

Ручных шагов (pgAdmin, SQL-скрипты, отдельные команды сида) нет.

| Что | Адрес |
|---|---|
| Дашборд | http://localhost:3000 |
| Документация API (Scalar) | http://localhost:8080/scalar/v1 |
| Документация API (Swagger UI) | http://localhost:8080/swagger |
| Проверка API | http://localhost:8080/api/health |
| PostgreSQL | `localhost:5432`, база `sales_dashboard`, пользователь и пароль `postgres` |

Остановить: `Ctrl+C` или `docker compose down`.
Сбросить данные и сгенерировать заново: `docker compose down -v && docker compose up --build`.

> Если на компьютере уже запущен PostgreSQL на порту 5432, контейнер `db` не стартует. Поменяйте в `docker-compose.yml` проброс порта на `"5433:5432"`: контейнеры общаются между собой по внутренней сети, на них это не повлияет.

## Локальная разработка без Docker

### Требования

- .NET SDK 8
- Node.js 18+ (проверено на 18.13, npm 8.19)
- PostgreSQL 14+ (локально или в Docker: `docker compose up db`)

### Backend

```bash
cd backend
dotnet run --project src/SalesDashboard.Api
```

Или откройте `backend/SalesDashboard.sln` в Visual Studio и запустите профиль `SalesDashboard.Api`. API поднимется на http://localhost:8080, браузер откроет Scalar.

Строка подключения по умолчанию лежит в `appsettings.json`: `Host=localhost;Port=5432;Database=sales_dashboard;Username=postgres;Password=postgres`. Базу создавать не нужно, её создаст EF при первом запуске.

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Дашборд откроется на http://localhost:5173. Vite проксирует запросы `/api/*` на `http://localhost:8080`, поэтому API должен быть запущен.

### Полезные команды

| Команда | Где | Что делает |
|---|---|---|
| `dotnet test` | `backend/` | юнит-тесты бэкенда |
| `npm test` | `frontend/` | тесты фронтенда |
| `npm run typecheck` | `frontend/` | проверка типов TypeScript |
| `npm run build` | `frontend/` | production-сборка в `frontend/dist` |

## Бизнес-правила и метрики

Все правила реализованы на сервере в `Domain/`. Каждое правило существует в одном месте кода.

### Статусы продаж

| Статус | Как учитывается |
|---|---|
| `Paid` | Во всех метриках |
| `Cancelled` | Продажа не состоялась. Не учитывается нигде |
| `Refunded` | **Полный возврат**: выручка и прибыль по продаже равны 0, в количество продаж и средний чек она не входит |

**Почему так трактуется Refunded.** В задании трактовка оставлена на усмотрение. Считать возврат нулевой выручкой — самая консервативная и честная для руководителя трактовка: деньги у компании не остались, значит, выручки нет. Частичных возвратов в модели нет.

Правило задано один раз: `SaleRules.CountsTowardsRevenue` (`Domain/Analytics/SaleRules.cs`). Это `Expression<Func<Sale, bool>>`, поэтому EF Core переводит его в SQL `WHERE`, а все запросы используют одно и то же правило.

### Формулы

| Метрика | Формула | Если данных нет |
|---|---|---|
| Выручка | Σ `quantity × unit_price` по оплаченным продажам | 0 |
| Себестоимость | Σ `quantity × unit_cost` по оплаченным продажам | 0 |
| Валовая прибыль | Выручка − Себестоимость | 0 |
| Маржа | Валовая прибыль / Выручка | `null` («—»), а не 0% |
| Количество продаж | число оплаченных продаж | 0 |
| Средний чек | Выручка / Количество продаж | `null` («—») |

- Цена продажи (`unit_price`, уже со скидкой) и себестоимость (`unit_cost`) хранятся в позиции продажи **как снимок на момент продажи**. Если цена товара потом изменится, история не пересчитается.
- Деньги везде хранятся как `decimal` / `numeric(18,2)`, без `double`.
- Маржа может быть **отрицательной** (продажа ниже себестоимости), это не ошибка.
- Расчёты реализованы в `KpiCalculator` как чистые функции без обращения к базе и покрыты тестами.

### Динамика к предыдущему периоду

| Метрика | Формат изменения |
|---|---|
| Выручка, прибыль, количество, средний чек | относительное: `(текущее − прошлое) / |прошлое|`, например +12,3 % |
| Маржа | абсолютное, в процентных пунктах: 20% → 25% это **+5 п.п.**, а не +25% |
| Прошлое значение 0 или не определено | `null` («—»): «рост на ∞%» ничего не сообщает |

Модуль в знаменателе нужен, чтобы выход из убытка в прибыль показывался как рост.

### Периоды

Периоды считаются в **бизнес-датах** в часовом поясе компании (`Dashboard:TimeZone`), а в базу запрос уходит в UTC.

| Пресет | Текущий период | С чем сравнивается |
|---|---|---|
| Сегодня | сегодня | вчера |
| 7 дней | последние 7 дней, включая сегодня | предыдущие 7 дней |
| 30 дней (по умолчанию) | последние 30 дней, включая сегодня | предыдущие 30 дней |
| Этот месяц | с 1-го числа по сегодня | **те же дни прошлого месяца** (1–24 сентября ↔ 1–24 августа), но не дальше конца месяца (31 марта ↔ весь февраль) |
| Прошлый месяц | весь прошлый календарный месяц | позапрошлый месяц целиком |
| Произвольный | даты «с» и «по» включительно | такой же по длине период перед ним |

Как устроены границы:
- Интервал **полуоткрытый** `[from, to)`: продажа в 23:59:59 последнего дня попадает в период, продажа в 00:00 следующего дня — нет. Смежные периоды не пересекаются и не теряют продажи на границе.
- «Сегодня» определяется по часовому поясу компании, а не по UTC: в 01:30 по Москве уже наступил новый день, хотя по UTC ещё вчера.
- Для произвольного периода обязательны обе даты, `to ≥ from`, длина не больше 366 дней. Иначе API возвращает `400` с понятным сообщением.
- Логика живёт в `PeriodResolver`, а текущее время берётся из `TimeProvider`, а не из `DateTime.Now`, поэтому её можно протестировать на любую дату.

### Рейтинг менеджеров

- Два режима сортировки: по **валовой прибыли** и по **среднему чеку**.
- **Равные значения получают одно место**: 1, 1, 3. Внутри равенства порядок детерминированный: по выручке, затем по имени, затем по id. Строки не «прыгают» между запросами.
- **Менеджер без продаж** за период остаётся в рейтинге с нулями (в интерфейсе строка приглушена). При сортировке по среднему чеку такие менеджеры стоят в конце.
- **Неактивные (уволенные) менеджеры** показываются, только если у них есть продажи в выбранном периоде.
- «Динамика» в рейтинге — относительное изменение метрики, по которой идёт сортировка, к предыдущему периоду.
- «Лучший менеджер» в KPI — первое место рейтинга по прибыли среди тех, у кого есть продажи. Отдельной логики для этого нет, переиспользуется тот же рейтинг.

### Граничные случаи из задания

| Случай | Как обработан |
|---|---|
| Отменённые и возвращённые продажи | исключаются правилом `SaleRules`, трактовка описана выше |
| Менеджер без продаж | в рейтинге с нулями, средний чек и маржа «—» |
| Одинаковые результаты у менеджеров | общее место и детерминированный порядок |
| Продажи на границе дат | полуоткрытый интервал, границы в часовом поясе компании |
| Очень крупные и очень мелкие сделки | `numeric(18,2)`. В сиде есть корпоративные заказы на 10–24 единицы профессиональной техники |
| Разная маржинальность | маржа считается от фактической выручки, отрицательная маржа допустима |
| Пустой период | деньги 0, отношения `null`. В UI пояснение вместо пустого блока |

## API

Базовый путь: `/api`. Формат JSON в camelCase, перечисления передаются строками. Интерактивная документация: `/scalar/v1` и `/swagger`.

### Общие параметры периода

| Параметр | Значения | По умолчанию |
|---|---|---|
| `preset` | `Today`, `Last7Days`, `Last30Days`, `CurrentMonth`, `PreviousMonth`, `Custom` | `Last30Days` |
| `from`, `to` | даты `yyyy-MM-dd`, включительно. Обязательны для `Custom` | — |

### `GET /api/dashboard/kpi`

KPI за период и динамика к предыдущему периоду.

```http
GET /api/dashboard/kpi?preset=Custom&from=2026-09-01&to=2026-09-24
```

```jsonc
{
  "period": { "from": "2026-09-01", "to": "2026-09-24", "previousFrom": "2026-08-01", "previousTo": "2026-08-24" },
  "revenue":      { "value": 18450000.00, "previous": 16900000.00, "change": 0.0917 },
  "grossProfit":  { "value": 4120000.00,  "previous": 3800000.00,  "change": 0.0842 },
  "margin":       { "value": 0.2233,      "previous": 0.2249,      "change": -0.0016 }, // change в долях: −0,16 п.п.
  "salesCount":   { "value": 312,         "previous": 295,         "change": 0.0576 },
  "averageCheck": { "value": 59134.62,    "previous": 57288.14,    "change": 0.0322 },
  "topManager":   { "id": 1, "fullName": "Анна Смирнова", "grossProfit": 612000.00 }
}
```

*Числа в примере условные.* `value`/`previous`/`change` могут быть `null`: значение не определено или сравнивать не с чем. `topManager` равен `null`, если в периоде нет продаж.

### `GET /api/dashboard/managers/ranking`

Рейтинг менеджеров.

| Параметр | Значения | По умолчанию |
|---|---|---|
| `sortBy` | `GrossProfit`, `AverageCheck` | `GrossProfit` |
| + параметры периода | | |

```jsonc
{
  "period": { "...": "..." },
  "sortBy": "GrossProfit",
  "items": [
    {
      "rank": 1, "managerId": 1, "fullName": "Анна Смирнова", "team": "Корпоративные продажи",
      "salesCount": 41, "revenue": 2750000.00, "grossProfit": 612000.00,
      "margin": 0.2225, "averageCheck": 67073.17, "change": 0.14
    }
  ]
}
```

### `GET /api/health`

Отвечает `{ "status": "ok" }`, когда API работает.

### Ошибки

Все ошибки возвращаются в формате **ProblemDetails (RFC 7807)**. Фронтенд показывает пользователю поле `detail`.

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "Некорректный запрос",
  "status": 400,
  "detail": "Дата окончания не может быть раньше даты начала."
}
```

| Код | Когда |
|---|---|
| 400 | неверный период: нет дат, `to < from`, больше 366 дней, неизвестный пресет или `sortBy` |
| 404 | неизвестный адрес |
| 500 | внутренняя ошибка. Детали пишутся в лог, наружу не отдаются |

## Модель данных

```
categories 1 ── * products 1 ── * sale_items * ── 1 sales * ── 1 managers
                                                        * ── 1 customers
```

| Таблица | Основные поля | Примечание |
|---|---|---|
| `managers` | `full_name`, `team`, `position`, `is_active` | |
| `customers` | `name`, `company`, `segment` (`Retail` / `Smb` / `Enterprise`) | сегмент хранится строкой |
| `categories` | `name` (unique) | |
| `products` | `name`, `sku` (unique), `category_id`, `list_price`, `unit_cost` | текущие прайс и себестоимость |
| `sales` | `manager_id`, `customer_id`, `sold_at_utc` (`timestamptz`), `status` | статус хранится строкой |
| `sale_items` | `sale_id`, `product_id`, `quantity` (> 0), `unit_price`, `unit_cost` | снимок цены и себестоимости на момент продажи |

- Имена таблиц и колонок в `snake_case` (`EFCore.NamingConventions`).
- Внешние ключи с `Restrict`, кроме `sale_items → sales` (`Cascade`).
- Check-ограничение: `quantity > 0`.

### Индексы

| Индекс | Под какой запрос |
|---|---|
| `sales (status, sold_at_utc)` | KPI: «оплаченные продажи за период» |
| `sales (manager_id, sold_at_utc)` | рейтинг: группировка по менеджеру в периоде. Заодно покрывает внешний ключ `manager_id` |
| `sales (sold_at_utc)` | запросы по дате (лента продаж, тренды) |
| `sale_items (sale_id)`, `sale_items (product_id)`, `products (category_id)`, `sales (customer_id)` | джойны по внешним ключам |
| `categories (name)`, `products (sku)` | уникальность |

### Как строятся запросы

- Фильтрация и агрегация выполняются **в PostgreSQL**. Продажи в память не загружаются, N+1 нет.
- KPI за период — три компактных агрегатных запроса (`COUNT` и две `SUM`). Рейтинг — две группировки по `manager_id`.
- Список менеджеров (около 20 строк) объединяется с агрегатами в памяти. Так в рейтинг попадают и менеджеры без продаж.
- Общие части запросов вынесены в `Infrastructure/Persistence/SalesQueries.cs`.

## Тестовые данные (seed)

Генератор: `Infrastructure/Seeding/DataSeeder.cs`. Запускается автоматически, если таблица `sales` пустая.

| Что | Объём |
|---|---|
| Менеджеры | 20 (один неактивный), 3 команды: корпоративные продажи, розница, онлайн |
| Клиенты | 80: ~60% частные лица, ~30% малый и средний бизнес, ~10% крупные компании |
| Каталог | 25 товаров в 8 категориях: дроны, профессиональные решения, экшн-камеры, стабилизаторы, микрофоны, питание, аксессуары, сервис |
| Продажи | примерно 3,5–4,5 тыс. за 12 месяцев до даты запуска (точное число пишется в лог API при сидировании) |

Чтобы данные были похожи на реальные, у каждого менеджера есть **профиль**:

| Профиль | Особенности |
|---|---|
| `Star` | много продаж, маленькие скидки, часто дорогая техника |
| `Solid` | средние показатели |
| `Discounter` | много продаж, но скидки до 20%, поэтому низкая маржа |
| `Newbie` | мало продаж, больше отмен и возвратов |

Дополнительно:
- у четырёх менеджеров в одном из месяцев **провал** (активность в 4 раза ниже обычной), у одного из них — в текущем;
- **сезонность**: летний пик дронов и предновогодний пик, в выходные продаж на 40% меньше;
- **отмены** 4–12% и **возвраты** 2–8% в зависимости от профиля;
- редкие **очень крупные корпоративные заказы** (10–24 единицы);
- маржа по категориям разная: от ~22% у дронов до ~70% у сервиса.

**Воспроизводимость.** `Random` с фиксированным seed и фиксированный порядок генерации дают одинаковые данные после пересоздания базы. Даты отсчитываются от дня запуска, поэтому пресеты «Сегодня» и «7 дней» всегда показывают данные.

## Архитектура

### Backend

```
backend/
├── SalesDashboard.sln
├── src/SalesDashboard.Api/
│   ├── Program.cs              композиция: DI, middleware, эндпоинты
│   ├── Common/                 BadRequestException, GlobalExceptionHandler → ProblemDetails
│   ├── Domain/                 чистый C# без EF и HTTP
│   │   ├── Entities/           Manager, Customer, Category, Product, Sale, SaleItem
│   │   ├── Periods/            DateRange, PeriodPreset, PeriodResolver, ReportingPeriod
│   │   └── Analytics/          SaleRules, KpiCalculator, ManagerRanking
│   ├── Features/               по папке на блок дашборда
│   │   ├── Common/             PeriodQuery, PeriodDto
│   │   ├── Kpi/                Endpoints + Service + Response
│   │   └── Ranking/            Endpoints + Service + Response
│   └── Infrastructure/
│       ├── DatabaseInitializer.cs   миграции + сид при старте
│       ├── Persistence/        AppDbContext, конфигурации, миграции, SalesQueries
│       └── Seeding/            DataSeeder, SeedCatalog, ManagerProfile
└── tests/SalesDashboard.Tests/ юнит-тесты домена
```

**Принятые решения и почему:**

- **Один проект API с разделением по папкам вместо четырёх проектов Clean Architecture.** Для объёма задачи этого достаточно: слои разделены, код легко найти, лишней обвязки нет. Домен не зависит от EF и HTTP, поэтому при росте проекта его легко вынести в отдельную сборку.
- **Vertical slices (`Features/*`).** Одна фича соответствует одному блоку UI и одному эндпоинту. Блоки загружаются и падают независимо, новый блок добавляется новой папкой.
- **Без Generic Repository и MediatR.** `DbContext` уже реализует Unit of Work и репозиторий. Лишняя обёртка спрятала бы `IQueryable` и помешала агрегировать данные в базе.
- **Бизнес-правила оформлены как чистые функции** (`KpiCalculator`, `ManagerRanking`, `PeriodResolver`) и тестируются без базы.
- **Specification через `Expression`** (`SaleRules`): одно правило статусов, которое EF переводит в SQL.
- **Value Object `DateRange`** с проверкой в конструкторе и полуоткрытым интервалом.
- **`TimeProvider` вместо `DateTime.Now`**: подменяется в тестах.
- **Единый формат ошибок** через `IExceptionHandler` и ProblemDetails.
- **Автоматическая инициализация базы** при старте: `docker compose up` работает без ручных шагов.

### Frontend

```
frontend/src/
├── main.tsx                 QueryClient (кэш, повторы только для сетевых и 5xx ошибок)
├── App.tsx                  раскладка страницы
├── api/                     HTTP-клиент (ApiError из ProblemDetails) и типы контракта
├── shared/
│   ├── format.ts            деньги, проценты, п.п., даты (Intl, ru-RU) — в одном месте
│   ├── period.ts            период в URL (?period=…&from=…&to=…)
│   └── ui/                  AsyncBlock, Skeleton/Error/Empty, Delta
└── features/
    ├── period/              PeriodPicker
    ├── kpi/                 useKpi + KpiCards
    └── ranking/             useRanking + ManagerRanking
```

- **TanStack Query для данных с сервера**: кэш, отмена устаревших запросов при смене периода, `keepPreviousData` без белого экрана.
- **Хуки как слой доступа к данным** (`useKpi`, `useRanking`): компоненты не знают про HTTP.
- **Один компонент для всех состояний блока** (`AsyncBlock`, см. ниже).
- **Период хранится в URL**: ссылкой можно поделиться, выбор сохраняется после перезагрузки, работает кнопка «назад».
- **Фронтенд ничего не считает**, только форматирует готовые значения.
- **В production** фронт раздаёт nginx, а `/api` проксируется на контейнер `api`. Фронт и API на одном origin, CORS не нужен.

## Фронтенд: состояния и UX

Все блоки обёрнуты в `AsyncBlock`, поэтому в каждом одинаково обработаны обязательные состояния:

| Состояние | Что видит пользователь |
|---|---|
| Первая загрузка | скелетон той же формы, что и контент |
| Смена периода или сортировки | прежние данные приглушены, пока грузятся новые, без мигания и белого экрана |
| Ошибка API | сообщение из ProblemDetails и кнопка «Повторить» |
| Пустой период | пояснение «За выбранный период…» вместо пустой таблицы |
| Нет значения метрики | «—» вместо 0% или NaN |

Микроанимации: появление KPI-карточек по очереди, подсветка строк при наведении, плавные переходы переключателей, shimmer у скелетона. При системной настройке «уменьшить движение» анимации отключаются. Вёрстка рассчитана на экран около 1440×900 и адаптируется к более узким.

## Решение проблем

| Симптом | Причина и решение |
|---|---|
| `3D000: база данных "postgres" не существует` | На сервере нет служебной базы `postgres`. Уже решено: EF создаёт базу через `template1` (`UseAdminDatabase`) |
| Контейнер `db` не стартует: `port is already allocated` | Порт 5432 занят локальным PostgreSQL. Поменяйте проброс на `"5433:5432"` |
| `npm install` зависает или `ECONNRESET` | Сеть или антивирус рвут соединение с реестром. Помогает `npm i --registry=https://registry.npmmirror.com`, отключение проверки HTTPS в антивирусе или другая сеть |
| В `.tsx` ошибки `react/jsx-runtime` / `JSX.IntrinsicElements` | Не установлены зависимости. Выполните `npm install` в `frontend/` и перезапустите IDE |
| `Unknown file extension ".tsx"` | `.tsx`-файл запускается через `node` напрямую. Фронтенд запускается командой `npm run dev` |
| Блоки дашборда показывают «Не удалось загрузить данные» | API не запущен или слушает не порт 8080 |
| Сообщения PostgreSQL выглядят как «кракозябры» | Русская локаль сервера в cp1251. Можно поставить `lc_messages = 'English_United States.1252'` в `postgresql.conf` |
